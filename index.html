    # ADR: move the core database from MySQL to AlloyDB
status  accepted · shipped · 0 rows lost
owner   eshan (benchmark → schema → CDC → validation → cutover)

## why
The roadmap needed AI search: vector embeddings for natural-language course
discovery. AlloyDB is Google's PostgreSQL-compatible database with vector search
built in, next to the app data. Getting there meant leaving MySQL.

## evidence first
Benchmarked both on identical 4 vCPU / 32 GB instances with the real Rails app:
~1.5M requests. Reads were a tie. Under a 2,000-signup burst AlloyDB had
0 failed signups (MySQL: 0.5%) and 39% better p95 write latency.

## decision
Heterogeneous migration with a blue-green cluster:
  · stream every change MySQL → AlloyDB with CDC while prod keeps running
  · build a second GKE cluster running dark against AlloyDB
  · at cutover: freeze, reconcile, fingerprint every table, flip DNS
  · MySQL is only ever read, so rollback stays a DNS flip away

## consequences
+ AlloyDB embeddings and RAG course discovery are unblocked (see wip/)
+ better write tail latency and reliability under bursts
- two engines, different types and SQL semantics, synced live
- MySQL-isms hide in app code (so I built a scanner, see tools/)

    $ ls /var/log/postmortems/ # bugs that threw no errors. click to open.

    DATA The script that deleted live rows while reporting success 
    symptom   a reconcile run finished "ALL DONE", yet ~10,400 rows were missing on the target
cause     the MySQL client defaulted to autocommit off + REPEATABLE READ, so the first
          SELECT pinned one snapshot for a multi-hour run. rows inserted mid-run were
          invisible to the script but already replicated by CDC, so they looked like
          "extras" and were deleted. the safety re-check read the same stale snapshot.
proof     every missing row's created_at sat in one 30-min band starting the second
          the script started
fix       autocommit on. a re-verify that shares the snapshot is not a safety check.
outcome   caught before cutover. cutover night: 0 rows lost
    DATA cancel vs drain: tens of millions of rows gone in one click 
    symptom   10 streaming jobs silently ran pinned at 2 workers. relaunching them fixed
          throughput, but ~183 tables came back short, some by 20M+ rows
cause     "--max-workers" alone does not enable autoscaling. and "cancel" drops data
          that was acked but not yet written. "drain" flushes it.
twist     draining the 4 biggest jobs forced a flush their 15 GB workers couldn't
          hold: OOM crash loop. moved them to 32 GB highmem workers.
fix       full re-backfill of all 183 tables, verified with exact COUNT(*) on both sides
lesson    drain, never cancel. estimated row counts are not evidence.
    DATA Rows that vanished with no error, no dead-letter, no trace 
    symptom   the same ~18k rows of one table failed to land on 4 backfills in a row.
          then a sweep found 24 tables stuck the same way.
cause     the streaming job's per-key dedup state was poisoned by earlier churn. it
          silently dropped any row whose sort key didn't beat the stored state.
proof     replayed one "lost" row by hand inside a rolled-back transaction: postgres
          accepted it. a fresh-state job then recovered the whole table.
lesson    recover with a fresh-state job, never by re-feeding the same one
    DATA Counts matched, checksums matched, data was 3.5 months old 
    symptom   found on cutover night: 177 records in the dead-letter queue were updates
          whose row already existed. right id, stale content.
why hidden row count matches, SUM(id) matches, fingerprint says MATCH, id-based
          reconcile never touches it. one row was 3.5 months stale.
fix       whole-table force-upsert of the 5 affected tables, inside the window
lesson    every check that compares ids is blind to content drift
    INFRA Connection storm with nothing in the logs 
    symptom   background workers hit "server closed the connection unexpectedly"
not it    not the worker, not connection lifetimes, not the database
cause     the connection pooler had its own autoscaler flapping 4→3→4 pods in two
          minutes. each scale-down sent SIGTERM, which the pooler treats as
          "exit now", killing every client on that pod. killed processes log nothing.
fix       preStop sends SIGINT (its graceful shutdown), 60s grace period,
          10-minute scale-down stabilization
    INFRA Deploys failing: "IP space exhausted" with half the cluster idle 
    symptom   a rolling deploy couldn't schedule pods, and the autoscaler couldn't add nodes
math      one /19 pod range shared by six clusters. at 110 max pods per node, each
          node reserves a /24 (256 IPs) → a hard ceiling of 32 nodes, total.
          real usage: ~14 pods per node. 12× over-reserved.
fix       new node pools at 32 max pods (/26 per node) on a fresh range: 4× denser
          per node, room for 1,024 nodes. rehearsed in staging with zero downtime.
lesson    max-pods is immutable on a pool. 33 costs the same as 64. 32 is the sweet spot.
    MEMORY A worker that ate 1.3 GB while doing nothing 
    symptom   messaging worker memory climbed 459 MB → 1,350+ MB and never came back
digging   live heap dumps via rbtrace: 135,970 APM Layer objects retained at idle.
          the APM agent stored each job's trace in a thread-local that was never
          cleared, so 10 threads each kept the previous job alive.
fix       APM off for background jobs + jemalloc decay tuned to 1s
result    idle RSS 1,350 MB (growing) → ~730 MB (stable), spike-and-release pattern

    # design rules I work to
1 the product backend never talks to video infrastructure. it asks the
  resource manager, which owns placement, capacity, VMs and recording.
2 recording is intent vs observed state. the host sets intent, a reconciler
  converges reality to it, so a crashed recorder heals itself. a human stop
  flips intent, which is how "stopped on purpose" differs from "crashed".
3 a self-hosted server dies mid-class → users reconnect onto LiveKit Cloud
  automatically, and recording resumes as cloud egress.
